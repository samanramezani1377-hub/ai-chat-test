# فهرست کنترل‌های رابط کاربری

**وضعیت:** 🔒 مرجع کنترل‌های UI بر اساس قابلیت‌های واقعی Core
**دامنه:** تعیین می‌کند هر قابلیت موجود در Core چه کنترل یا مسیر کاربری باید داشته باشد.

> 🔴 **الزام قطعی:** تمام متن‌های قابل مشاهده در UI باید فارسی و راست‌چین (RTL) باشند. نام‌های فنی، شناسه‌ها و مقادیر ذاتاً فنی در صورت نیاز می‌توانند LTR باشند.

## ۱. اصل مهم

این سند از روی قابلیت‌های واقعی فعلی Core تهیه شده است. چیزی که در کد وجود ندارد، به‌عنوان کنترل قطعی UI ثبت نمی‌شود.

وجود API یا Contract در Core به معنی قرارگرفتن کنترل آن در Header نیست؛ محل نمایش باید با Context مناسب تعیین شود.

## ۲. کنترل‌های Runtime و مدل

```text
Runtime
├── بارگذاری مدل
├── خارج‌کردن مدل از حافظه
├── تولید پاسخ
├── توقف تولید
└── مشاهده اطلاعات Runtime
```

### ۲.۱ بارگذاری مدل

کنترل UI: **بارگذاری مدل** در مسیر مدیریت مدل/Runtime.

### ۲.۲ خارج‌کردن مدل

کنترل UI: **خارج‌کردن مدل** در مسیر مدیریت مدل/Runtime و فقط وقتی وضعیت مدل اجازه آن را می‌دهد.

### ۲.۳ تولید پاسخ

کنترل UI اصلی: **ارسال** در Chat/Composer.

### ۲.۴ توقف تولید

طبق Q21، دکمه ارسال هنگام تولید به **توقف** تبدیل می‌شود:

```text
حالت عادی     [ ارسال ]
در حال تولید  [ توقف ]
```

### ۲.۵ اطلاعات Runtime

مسیر UI: لمس Runtime در Header برای مشاهده خلاصه و جزئیات مرتبط، مطابق تصمیم‌های مربوط به Runtime.

اطلاعات پایه Runtime شامل نام، نسخه و Backend در صورت ارائه واقعی توسط Core است.

## ۳. کنترل‌های Inference

Core برای هر درخواست `InferenceSettings` دریافت می‌کند:

```text
InferenceSettings
├── دما (temperature)
├── حداکثر توکن جدید (maxNewTokens)
├── Top-K
├── Top-P
├── Min-P
├── جریمه تکرار (repeatPenalty)
├── Seed
├── دنباله‌های توقف (stopSequences)
└── طول زمینه (contextLength)
```

این فیلدها تا زمانی که کنترل UI واقعی برای تغییرشان در Core/Presentation مشخص نشده، صرفاً به‌عنوان قابلیت دامنه مستند می‌شوند و UI نباید وانمود کند که آن‌ها را تغییر می‌دهد.

## ۴. کنترل‌های Conversation / Context

```text
Context
├── System Context
├── Persistent Task Context
├── Summary
├── پیام‌های اخیر
└── Workspace Context
```

همچنین `requestedRecentMessages` قابل تعیین است. این موارد فقط در صورت وجود قابلیت مدیریت واقعی، کنترل مستقیم UI دریافت می‌کنند.

## ۵. کنترل‌های Action

```text
Action Lifecycle
├── آماده‌سازی
├── اعتبارسنجی
├── درخواست تأیید
├── تأیید
├── رد
├── اجرا
├── تکمیل
├── شکست
└── تلاش مجدد
```

### ۵.۱ آماده‌سازی

نتیجه آماده‌سازی می‌تواند شامل executionId، actionId، ورودی، سطح ریسک و وضعیت باشد و وضعیت آن در Timeline مرکزی Workspace نمایش داده می‌شود.

### ۵.۲ اعتبارسنجی

اعتبارسنجی Capability موردنیاز را بررسی می‌کند. نبود Capability باید به خطای واقعی منجر شود و در عیب‌یابی قابل پیگیری باشد.

### ۵.۳ تأیید

Action با ریسک `SENSITIVE` نیازمند تأیید کاربر است. طبق تصمیم Workspace، کنترل‌های تأیید فقط وقتی نمایش داده می‌شوند که همان Action واقعاً در وضعیت نیازمند تأیید باشد:

```text
[ تأیید ]    [ رد ]
```

تأیید و رد از Workspace قابل انجام هستند.

### ۵.۴ اجرا

اجرای نهایی فقط پس از تأیید لازم انجام می‌شود. Workspace نمایش‌دهنده و کنترل‌کننده Contextual عملیات است، اما Executor مستقل نیست.

### ۵.۵ تلاش مجدد

برای اجرای شکست‌خورده، در صورت پشتیبانی واقعی، مسیر **تلاش مجدد** وجود دارد. اگر Recovery نیازمند بررسی یا مداخله کاربر باشد، اجرای کورکورانه مجاز نیست.

## ۶. Verification

```text
Verification
├── موفق
└── ناموفق
    └── evidence در صورت وجود
```

نتیجه Verification باید واقعی باشد و موفقیت صرفاً از متن مدل نتیجه‌گیری نشود.

در Workspace، Verification به‌عنوان Event همان Timeline نمایش داده می‌شود و در صورت نیاز جزئیات آن با Expand باز می‌شود.

## ۷. Recovery

```text
Recovery
├── قبلاً تکمیل شده
├── قابل تلاش مجدد
├── نیازمند بررسی
└── نیازمند مداخله کاربر
```

کنترل Recovery باید تطبیقی باشد و فقط عملیات واقعی و مجاز را نمایش دهد.

## ۸. Trace

Trace واقعی رویدادهای چرخه اجرای Action را ثبت می‌کند:

```text
Trace
├── آماده‌شده
├── اعتبارسنجی‌شده
├── درخواست تأیید
├── تأییدشده
├── ردشده
├── شروع اجرا
├── تکمیل اجرا
├── شکست Verification
├── شکست اجرا
└── درخواست تلاش مجدد
```

**در Workspace، Trace داخل همان Timeline و Event مربوط به Action ادغام می‌شود؛ Timeline جداگانه‌ای برای Trace وجود ندارد.**

گزارش فنی کامل Trace در عیب‌یابی قابل مشاهده است و از Workspace، «مشاهده جزئیات» باید Context همان execution/action را حفظ کند و به گزارش متناظر برسد.

## ۹. خطاها و گزارش عیب‌یابی

```text
خطا
├── پیام فارسی برای کاربر
├── خطای فنی خام
├── executionId
├── actionId
└── زمان
```

گزارش عیب‌یابی Trace و Errorهای همان اجرا را تجمیع می‌کند. داخل عیب‌یابی یک مسیر مستقل **«خطاها»** وجود دارد.

کارت‌های مربوط به کارهای حساس باید از کارت تأیید معمولی از نظر بصری متمایز باشند و جزئیات آن‌ها قابل مشاهده باشد. گزارش فارسی قابل ارائه برای تأیید نهایی اطلاعات حساس نیز باید از همان Context قابل دسترسی باشد.

## ۱۰. تنظیمات واقعی فعلی

```text
عیب‌یابی / Debug
└── نمایش جزئیات کامل خطا
```

این تنظیم فقط وقتی ارائه می‌شود که Core آن را واقعاً پشتیبانی کند.

Visibility هر Metric مستقل است و هر **دسته Performance نیز کنترل فعال/مخفی‌شدن مستقل** دارد.

## ۱۲. قرارداد Workspace

Workspace باید با Q31 تا Q35 منطبق باشد:

```text
Workspace
│
├── خلاصه اجرای جاری
│   ├── وضعیت
│   ├── مرحله فعلی
│   └── زمان سپری‌شده در صورت وجود واقعی
│
└── Timeline مرکزی
    ├── Event / Action
    │   ├── وضعیت و نتیجه خلاصه
    │   ├── Metricهای پردازشی کوچک و کم‌رنگ
    │   ├── کنترل‌های مجاز همان لحظه
    │   └── ▼ Expand
    │       ├── ▼ اطلاعات درخواست
    │       ├── ▼ پردازش و Trace
    │       ├── ▼ Preview / Result
    │       └── مشاهده جزئیات → عیب‌یابی همان Execution
    └── ...
```

### قواعد Workspace

- Timeline مرکز بصری صفحه است.
- پنل Contextual مستقل و ثابت وجود ندارد؛ اطلاعات Contextual داخل Expand لایه‌ای همان Event قرار دارد.
- جزئیات از پایین همان Event Expand می‌شوند.
- کنترل‌ها Context-aware هستند و فقط قابلیت‌های واقعی و مجاز همان Action/وضعیت را نشان می‌دهند.
- اطلاعات پردازشی ثانویه کوچک‌تر و کم‌رنگ‌تر هستند.
- Progress Bar درصدی برای اجرای جاری وجود ندارد.
- Preview/Result فقط در صورت وجود واقعی نمایش داده می‌شود.
- خروجی‌های بزرگ نباید Timeline را شلوغ کنند.
- Before/After فقط در صورت وجود داده واقعی نمایش داده می‌شود.
- «مشاهده جزئیات» Context همان Execution را حفظ می‌کند و به گزارش متناظر در عیب‌یابی می‌رود.
- هیچ کنترل یا Metric ساختگی، Mock یا تخمینی مجاز نیست.
