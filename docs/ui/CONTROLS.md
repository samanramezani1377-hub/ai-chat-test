# فهرست کنترل‌های رابط کاربری

**وضعیت:** 🔒 مرجع کنترل‌های UI بر اساس قابلیت‌های واقعی Core
**دامنه:** تعیین می‌کند هر قابلیت موجود در Core چه کنترل یا مسیر کاربری باید داشته باشد.

> 🔴 **الزام قطعی:** تمام متن‌های قابل مشاهده در UI باید فارسی و راست‌چین (RTL) باشند. نام‌های فنی، شناسه‌ها و مقادیر ذاتاً فنی در صورت نیاز می‌توانند LTR باشند.

## ۱. اصل مهم

این سند از روی قابلیت‌های واقعی فعلی Core تهیه شده است. چیزی که در کد وجود ندارد، به‌عنوان کنترل قطعی UI ثبت نمی‌شود.

همچنین وجود یک API یا Contract در Core به معنی آن نیست که کنترل آن باید در Header قرار بگیرد؛ محل نمایش و کنترل باید با Context مناسب تعیین شود.

## ۲. کنترل‌های Runtime و مدل

قرارداد Runtime فعلی این عملیات را ارائه می‌کند:

```text
Runtime
├── بارگذاری مدل
├── خارج‌کردن مدل از حافظه
├── تولید پاسخ
├── توقف تولید
└── مشاهده اطلاعات Runtime
```

این قابلیت‌ها از قرارداد `ModelRuntime` می‌آیند.

### ۲.۱ بارگذاری مدل

کنترل UI: **بارگذاری مدل** در مسیر مدیریت مدل/Runtime.

### ۲.۲ خارج‌کردن مدل

کنترل UI: **خارج‌کردن مدل** در مسیر مدیریت مدل/Runtime.

این کنترل نباید بدون توجه به وضعیت فعلی مدل فعال باشد.

### ۲.۳ تولید پاسخ

کنترل UI اصلی: **ارسال** در Chat/Composer.

### ۲.۴ توقف تولید

کنترل UI طبق Q21: دکمه ارسال هنگام تولید به **توقف** تبدیل می‌شود.

```text
حالت عادی     [ ارسال ]
در حال تولید  [ توقف ]
```

### ۲.۵ اطلاعات Runtime

کنترل/مسیر UI: لمس Runtime در Header برای مشاهده خلاصه و جزئیات مرتبط، مطابق Q25.

اطلاعات پایه Runtime شامل نام، نسخه و Backend قابل ارائه است.

## ۳. کنترل‌های Inference

Core برای هر درخواست `InferenceSettings` دریافت می‌کند. فیلدهای واقعی فعلی عبارت‌اند از:

```text
InferenceSettings
├── دما (temperature)
├── حداکثر توکن جدید (maxNewTokens)
├── Top-K
├── Top-P
├── Min-P
├── جریمه تکرار (repeatPenalty)
├── Seed
├── دنباله‌های توقف (stopSequences)
└── طول زمینه (contextLength)
```

### وضعیت UI این کنترل‌ها

این فیلدها در Contract دامنه وجود دارند، اما در نسخه فعلی Core **کنترل UI مستقلی برای تغییر آن‌ها پیاده نشده است**.

بنابراین فعلاً فقط به‌عنوان **تنظیمات قابل مدیریت Inference** مستند می‌شوند و نباید ادعا شود که UI فعلی آن‌ها را تغییر می‌دهد.

محل تصمیم‌گیری برای ارائه این کنترل‌ها در UI از طریق **Q26** تعیین خواهد شد.

## ۴. کنترل‌های Conversation / Context

Context واقعی مورد استفاده برای ساخت درخواست شامل این بخش‌هاست:

```text
Context
├── System Context
├── Persistent Task Context
├── Summary
├── پیام‌های اخیر
└── Workspace Context
```

همچنین تعداد پیام‌های اخیر درخواست‌شده (`requestedRecentMessages`) قابل تعیین است.

این موارد الزاماً کنترل مستقیم UI نیستند؛ UI فقط باید در صورت ارائه قابلیت مدیریت Context، مسیر مشخص و واقعی برای آن داشته باشد.

## ۵. کنترل‌های Action

سیستم Action این قابلیت‌های واقعی را دارد:

```text
Action Lifecycle
├── آماده‌سازی
├── اعتبارسنجی
├── درخواست تأیید
├── تأیید
├── رد
├── اجرا
├── تکمیل
├── شکست
└── تلاش مجدد
```

### ۵.۱ آماده‌سازی

نتیجه آماده‌سازی شامل شناسه اجرا، شناسه Action، ورودی، سطح ریسک و وضعیت است.

UI باید بتواند وضعیت آماده‌سازی را در Workspace نمایش دهد.

### ۵.۲ اعتبارسنجی

اعتبارسنجی قابلیت موردنیاز را بررسی می‌کند. در صورت نبود Capability، خطای واقعی ثبت می‌شود.

### ۵.۳ تأیید

Action با ریسک `SENSITIVE` نیازمند تأیید کاربر است.

UI باید برای این حالت کنترل‌های:

```text
[ تأیید ]    [ رد ]
```

داشته باشد.

### ۵.۴ اجرا

اجرای نهایی فقط پس از تأیید لازم انجام می‌شود.

Workspace نمایش‌دهنده نتیجه است و Executor نیست.

### ۵.۵ تلاش مجدد

برای اجرای شکست‌خورده مسیر **تلاش مجدد** وجود دارد. اگر Recovery تشخیص دهد اجرای مجدد نیازمند بررسی یا مداخله کاربر است، UI نباید مستقیماً اجرا را تکرار کند.

## ۶. Verification

نتیجه Action می‌تواند Verification داشته باشد:

```text
Verification
├── موفق
└── ناموفق
    └── evidence در صورت وجود
```

UI باید نتیجه Verification واقعی را نمایش دهد و موفقیت را صرفاً از متن مدل نتیجه‌گیری نکند.

## ۷. Recovery

Recovery واقعی این تصمیم‌ها را ارائه می‌کند:

```text
Recovery
├── قبلاً تکمیل شده
├── قابل تلاش مجدد
├── نیازمند بررسی
└── نیازمند مداخله کاربر
```

بنابراین UI باید برای هر وضعیت مسیر مناسب داشته باشد؛ مخصوصاً در حالت‌های «نیازمند بررسی» و «نیازمند مداخله کاربر» نباید دکمه اجرای کورکورانه نمایش داده شود.

## ۸. Trace

سیستم Trace واقعی رویدادهای چرخه اجرای Action را ثبت می‌کند، از جمله:

```text
Trace
├── آماده‌شده
├── اعتبارسنجی‌شده
├── درخواست تأیید
├── تأییدشده
├── ردشده
├── شروع اجرا
├── تکمیل اجرا
├── شکست Verification
├── شکست اجرا
└── درخواست تلاش مجدد
```

همچنین Execution Trace سطح بالاتری از چرخه عملیات دارد که شامل آماده‌سازی، اعتبارسنجی، تأیید، اجرا، Verification، شکست و Recovery است.

Trace باید در **عیب‌یابی** قابل مشاهده باشد و با Action Detail قابل ارتباط باشد.

## ۹. خطاها و گزارش عیب‌یابی

سیستم خطای Action را با دو سطح داده نگهداری می‌کند:

```text
خطا
├── پیام فارسی برای کاربر
├── خطای فنی خام
├── executionId
├── actionId
└── زمان
```

گزارش عیب‌یابی نیز Trace و Errorهای همان اجرا را تجمیع می‌کند و امکان تهیه متن قابل کپی دارد.

طبق Q38، داخل **عیب‌یابی** یک مسیر مستقل **«خطاها»** وجود خواهد داشت.

## ۱۰. تنظیمات واقعی فعلی

در Core Settings، تنظیم فعلی مشخص و واقعی عبارت است از:

```text
عیب‌یابی / Debug
└── نمایش جزئیات کامل خطا
```

این تنظیم می‌تواند فعال یا غیرفعال شود.

## ۱۱. Performance

Metricهای تعریف‌شده پروژه در سند Performance Metrics مستند هستند:

```text
Performance
├── Inference
│   ├── First Token Time
│   ├── Input Tokens
│   ├── Output Tokens
│   ├── Generation Time
│   ├── Tokens/sec
│   └── Context Usage
├── Model
│   ├── Load Time
│   └── Unload Time
├── Device
│   ├── RAM
│   ├── CPU
│   ├── GPU/NPU در صورت دسترسی واقعی
│   └── Backend
├── Agent
│   ├── Total Agent Time
│   ├── Step Count
│   ├── Action Time
│   ├── Retry Count
│   └── Error Count
└── Network
    ├── Request/Connectionهای واقعی
    └── Network Usage در حد داده واقعی Android/Runtime
```

تمام Metricها باید واقعی باشند و مقدار ساختگی یا Mock مجاز نیست.

Visibility هر Metric مستقل است و طبق Q40 علاوه بر کنترل مستقل Metric، هر **دسته Performance نیز کنترل فعال/مخفی‌شدن مستقل** دارد.

## ۱۳. قواعد قطعی

- هیچ کنترل UI برای قابلیت غیرموجود در Core به‌عنوان قابلیت قطعی ثبت نمی‌شود.
- وجود یک Contract در Core به‌تنهایی مجوز نمایش کنترل در Header نیست.
- کنترل‌های UI باید به Operation/Contract واقعی متصل شوند.
- هیچ دکمه‌ای نباید نتیجه موفقیت را بدون Verification واقعی اعلام کند.
- مقدار ساختگی، Mock و Placeholder برای وضعیت یا Metric ممنوع است.
- کنترل‌های حساس باید مسیر تأیید واقعی داشته باشند.
- متن UI فارسی و RTL است.
- این سند مرجع موجودی کنترل‌هاست؛ محل دقیق کنترل‌هایی که هنوز سؤال طراحی آن‌ها باز است، از طریق بانک سؤالات UI تعیین می‌شود.
