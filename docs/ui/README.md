# مستندات رابط کاربری

**وضعیت:** 🔒 مشخصات UI v1 یکپارچه و آماده قفل نهایی
**نسخه هدف:** UI v1.0.0

> 🔴 **قانون اجباری: کل رابط کاربری برنامه باید فارسی و راست‌چین (RTL) باشد.** این قانون بدون استثنا برای Header، Sidebar، گفت‌وگو، فضای کار، تنظیمات، عیب‌یابی، درباره برنامه، Menu، Dialog، Button، Status، Error، Empty State و تمام متن‌های قابل مشاهده اعمال می‌شود. داده‌های ذاتاً فنی مانند نام مدل، کد، URL و شناسه فنی می‌توانند LTR باشند، اما متن و ساختار پیرامون آن‌ها فارسی و RTL باقی می‌ماند.

## خلاصه UI مصوب

### Header

سه ناحیه دارد:

```text
[ گفت‌وگو │ کار │ ⋯ ]    ● آماده
                          مدل محلی       [ ☰ ]
```

- گروه سمت چپ کمتر از نصف عرض است.
- گفت‌وگو/کار با خط ظریف زیر گزینه فعال مشخص می‌شوند.
- `⋯` شامل «لاگ» و «تنظیمات» است.
- Runtime محلی دوخطی است و ارتفاع آن با دکمه‌های Header برابر است.
- `☰` گرد و در سمت راست است.
- کنترل دائمی دیگری لازم نیست.

### Sidebar

از سمت راست باز می‌شود و Overlay نیمه‌شفاف روی محتوای اصلی دارد.

```text
گفت‌وگوی جدید

ابزار
├── فضای کار
├── عیب‌یابی
└── تنظیمات

اطلاعات
└── درباره برنامه

اخیر
├── گفت‌وگوی فعلی
├── گفت‌وگوی ۱
├── گفت‌وگوی ۲
├── گفت‌وگوی ۳
├── گفت‌وگوی ۴
├── گفت‌وگوی ۵
└── مشاهده بیشتر
```

### گفت‌وگوهای اخیر

- عنوان + وضعیت + زمان.
- زمان در سمت چپ، کوچک و خاکستری کم‌رنگ.
- گفت‌وگوی فعلی با Highlight ظریف + Indicator مشخص می‌شود.
- «مشاهده بیشتر» هر بار ۵ مورد دیگر اضافه می‌کند.
- کلیک/لمس گفتگو آن را باز می‌کند.
- Long Press منوی «باز کردن / تغییر نام / حذف» را از همان نقطه باز می‌کند.
- حذف قرمز است و حذف گفتگو با Undo ده‌ثانیه‌ای همراه است.

### Chat

- پیام کاربر: حباب نیمه‌شفاف با رنگ روشن و آرام، با جهت بصری آبی روشن.
- پاسخ مدل: بدون حباب سنگین و مبتنی بر Typography و فاصله‌گذاری.
- Composer: Floating و Responsive.

### Composer و ارسال

- موبایل: جمع‌وجور و شناور.
- تبلت: کمی بزرگ‌تر.
- دسکتاپ: عرض محدود و مرکزگرا.
- Composer سقف ارتفاع دارد و بعد از آن متن داخلی Scroll می‌شود.
- دکمه ارسال گرد و تطبیقی است.
- دسکتاپ: `Enter` خط جدید، `Shift + Enter` ارسال.
- موبایل: Enter خط جدید، ارسال فقط با دکمه.

### Runtime

```text
● آماده
مدل محلی
```

وضعیت‌ها:

- آماده
- در حال کار
- در حال تولید
- خارج از دسترس
- خطا

هر وضعیت رنگ مخصوص خود را دارد؛ وضعیت‌های فعالیت Pulse ظریف دارند. رنگ تنها روش تشخیص نیست.

## موجودی کنترل‌ها

فهرست کامل کنترل‌های استخراج‌شده از قابلیت‌های واقعی Core در [`CONTROLS.md`](CONTROLS.md) نگهداری می‌شود. این فایل مرجع است تا هیچ قابلیت واقعی Core بدون مسیر UI باقی نماند و در عین حال قابلیت غیرموجود به UI اضافه نشود.

## قواعد تغییر

۱. تا زمان تأیید نهایی UI، کد UI اضافه نمی‌شود.
۲. بعد از قفل، هر تغییر UI باید ابتدا در مستندات ثبت و نسخه‌بندی شود.
۳. تغییر UI نباید Core، تست‌ها یا Performance را تضعیف کند.
۴. Mock و Placeholder نباید جای وضعیت واقعی برنامه را بگیرند.
۵. CI معیار صحت پیاده‌سازی فنی است، نه مرجع تصمیم طراحی.
۶. تغییر ساختار UI ابتدا باید در [`UI_TREE.md`](UI_TREE.md) ثبت شود.
