# سؤال ۲۷ — نمایش Action Trace

**وضعیت:** 🔒 تصمیم‌گیری شد

## تصمیم نهایی

**گزینه E — ترکیبی**

Action Trace باید در سه سطح قابل دسترسی باشد:

```text
Action Trace
│
├── اجرای فعلی
│   └── خلاصه Trace در فضای کار
│
├── جزئیات اجرای ثبت‌شده
│   └── Trace همان اجرا در جزئیات تاریخچه عملکرد
│
└── عیب‌یابی
    └── Trace کامل و خام فنی
```

### رویدادهای واقعی قابل نمایش

Core برای هر `executionId` رویدادهای زیر را ثبت می‌کند:

- آماده‌سازی (`PREPARED`)
- اعتبارسنجی (`VALIDATED`)
- درخواست تأیید (`APPROVAL_REQUESTED`)
- تأیید (`APPROVED`)
- رد (`REJECTED`)
- شروع اجرا (`EXECUTION_STARTED`)
- پایان موفق اجرا (`EXECUTION_COMPLETED`)
- شکست Verification (`VERIFICATION_FAILED`)
- شکست اجرا (`EXECUTION_FAILED`)
- درخواست Retry (`RETRY_REQUESTED`)

هر رویداد می‌تواند دارای `executionId`، نوع رویداد، پیام و زمان ثبت باشد.

### رفتار UI

- خلاصه Trace اجرای فعلی در Workspace قابل مشاهده است.
- Trace همان اجرا در جزئیات اجرای Q24 قابل مشاهده و Expand است.
- Trace کامل و جزئیات خام فنی در عیب‌یابی قابل بررسی است.
- Trace به‌صورت Timeline نمایش داده می‌شود.
- رویدادهای تأیید، رد، خطا، Verification و Retry باید از نظر بصری قابل تشخیص باشند.
- Trace نباید به‌عنوان داده دائمی فرض شود مگر اینکه لایه ذخیره‌سازی واقعی برای آن فراهم شده باشد.
- UI نباید رویداد، زمان یا نتیجه‌ای را که Core گزارش نکرده است جعل کند.

## زبان و راست‌چین

تمام متن‌ها و اجزای این مسیر باید فارسی و راست‌چین (RTL) باشند.
