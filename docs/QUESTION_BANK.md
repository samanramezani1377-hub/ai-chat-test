## پاسخ‌ها

### 01 — هدف اصلی Prototype
**وضعیت:** تصمیم ثبت شد

**پاسخ:**

هدف Prototype دو بخش اصلی دارد:

1. **ارزیابی توانایی مدل و سیستم:** بررسی اینکه مدل برای کارهایی که قرار است انجام دهد چقدر توانایی دارد، کیفیت خروجی آن چگونه است، و خروجی‌ها تا چه اندازه امن و قابل اعتماد هستند.
2. **ساخت یک Base قابل استفاده مجدد:** Prototype باید یک پایه عملی و قابل اتکا ایجاد کند تا در آینده بتوان قابلیت Local AI را راحت‌تر و با ریسک کمتر در پروژه **WooGit** پیاده‌سازی کرد.

بنابراین پروژه فقط یک Chat Demo نیست؛ یک محیط آزمایشی برای ارزیابی **Capability، Safety/Reliability و قابلیت انتقال معماری به WooGit** است.

### 02 — مدل پایه
**وضعیت:** تصمیم ثبت شد

**پاسخ:**

مدل پایه برای طراحی و توسعه Prototype، **Qwen3-1.7B** است.

این انتخاب به‌عنوان مدل مرجع طراحی انجام شده است، اما مدل نباید داخل APK بسته‌بندی شود. فایل مدل باید جداگانه تهیه و توسط کاربر در اپ **Import** شود.

معماری باید از ابتدا به‌صورت **Model-Agnostic** طراحی شود؛ یعنی Qwen3-1.7B مدل پایه و مدل هدف فعلی باشد، اما ساختار Import/Validation/Loading/Inference به یک مدل خاص قفل نشود تا در آینده بتوان مدل‌های سازگار دیگری را نیز بدون بازطراحی اساسی اپ وارد و اجرا کرد.

**اصل تصمیم:**
- مدل پیش‌فرض/مرجع: Qwen3-1.7B
- مدل داخل APK: خیر
- دریافت مدل: جداگانه
- ورود مدل به اپ: Import
- قابلیت Import مدل‌های آینده: الزامی
- وابستگی معماری به یک مدل خاص: ممنوع

### 05 — روش Import مدل
**وضعیت:** تصمیم ثبت شد

**پاسخ:**

مدل باید **جدا از APK** تهیه شود و کاربر آن را مستقیماً از طریق قابلیت **Import Model** وارد اپ کند.

فرآیند موردنظر:

1. کاربر گزینه **Import Model** را انتخاب می‌کند.
2. فایل مدل را از حافظه/Files دستگاه انتخاب می‌کند.
3. اپ فایل را بررسی و اعتبارسنجی می‌کند.
4. مدل به فضای اختصاصی مدیریت مدل‌های اپ کپی/ثبت می‌شود.
5. مدل در فهرست مدل‌های قابل استفاده نمایش داده می‌شود.
6. کاربر می‌تواند مدل را Load کرده و برای Chat/Inference استفاده کند.

این سیستم باید از ابتدا عمومی طراحی شود تا بعداً مدل‌های سازگار دیگر نیز با همین فرآیند قابل Import باشند و معماری به Qwen3-1.7B وابسته نشود.

**اصل تصمیم:**
- مدل داخل APK: خیر
- دریافت مدل: جداگانه
- ورود مدل: Import توسط کاربر
- اعتبارسنجی قبل از استفاده: الزامی
- نمایش مدل‌های Import‌شده: الزامی
- پشتیبانی از مدل‌های آینده: الزامی

### 06 — محل نگهداری مدل‌ها

مدیریت مدل‌ها باید امکان شناسایی مدل Import‌شده، نگهداری مستقل چند مدل و استفاده از مسیر اختصاصی اپ را فراهم کند.

**اصل تصمیم:**

- وابستگی اجرای مدل به فایل اصلی خارج از اپ: خیر
- پشتیبانی از چند مدل: حفظ شود
- دسترسی مستقیم سایر اپ‌ها به فایل‌های مدل: تا حد امکان محدود شود

### 07 — وضعیت APK بدون مدل

پس از Import موفق مدل، مدل در فضای اختصاصی اپ قرار گرفته و قابلیت Chat/Inference فعال می‌شود.

**پاسخ:**

برای Prototype، بخش Chat باید علاوه بر قابلیت‌های پایه، امکانات لازم برای تست دقیق مدل، Inference و Agent را نیز داشته باشد.

**قابلیت‌های ۱ تا ۲۰ مورد توافق قرار گرفتند:**

1. ارسال پیام
2. دریافت پاسخ مدل

4. New Chat
5. پاک‌کردن مکالمه
6. Streaming پاسخ
7. Stop Generation
8. نمایش وضعیت مدل شامل Loaded / Loading / Unloaded / Error
9. نمایش خطاهای واقعی
10. اجرای کاملاً Offline
11. نمایش وضعیت در حال تولید پاسخ
12. غیرفعال‌سازی ارسال در وضعیت‌های نامعتبر
13. امکان ادامه Generation پس از خطا یا Stop، در صورت پشتیبانی Runtime
14. شمارش توکن‌های ورودی و خروجی
15. نمایش سرعت Generation برحسب tok/s
16. اندازه‌گیری زمان رسیدن اولین Token
17. اندازه‌گیری زمان کل Generation
18. نمایش میزان مصرف Context
19. نمایش مدل فعال و مشخصات آن
20. نمایش تنظیمات فعلی Inference

**قابلیت‌های Debug و Agent مورد توافق:**

33. نمایش Raw Model Output برای بررسی خروجی خام مدل
34. Agent Debug Mode برای نمایش مسیر کامل اجرای Agent، شامل Model → Action Request → Parser → Executor → Tool Result → Final Answer
35. درخواست تأیید کاربر قبل از اجرای Actionهای حساس
36. ثبت Action Log برای Actionهای اجراشده
37. نمایش Tool Result به‌صورت جدا از پاسخ نهایی AI

این قابلیت‌ها باید به‌صورت واقعی پیاده‌سازی شوند و در Prototype قابلیت‌های Mock یا رفتار جعلی وجود نداشته باشد.

### 09 — Streaming پاسخ
**وضعیت:** تصمیم ثبت شد

**پاسخ:**

بله، **Streaming واقعی پاسخ الزامی است**.

پاسخ مدل باید هنگام Generation به‌صورت تدریجی از Runtime دریافت و در UI نمایش داده شود و نباید تا پایان Generation به‌صورت یک‌جا نمایش داده شود.

Streaming باید از Runtime تا UI به‌صورت واقعی پیاده‌سازی شود و امکان اندازه‌گیری **First Token Time** و **Generation Speed (tok/s)** را فراهم کند.

همچنین Streaming باید با قابلیت **Stop Generation** سازگار باشد تا Generation فعال بتواند در زمان تولید متوقف شود.
